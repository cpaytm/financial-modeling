Part 13. 기존 재무모델링의 출발점

기존 방식의 한계

Excel은 계산과 수식 검토에는 강하지만, 모델의 사업 논리와 드라이버 관계를 보여주는 데는 약함.

전통적 출발점

  • Excel에서 바로 시작
  • 과거 실적 입력
  • 매출과 비용 수식 작성
  • 가정 시트와 결과표 구성

구조적 문제

  • 수식은 많아지지만 모델 논리는 잘 보이지 않음
  • 셀 참조는 연결되어도 사업모델 구조는 숨음
  • 공유 드라이버가 잘 드러나지 않음
Part 14. 이 강의가 바꾸려는 순서

작업 순서를 바꾼다

Excel을 버리는 것이 아니라, Excel에 들어가기 전 모델 구조를 먼저 드러냄

기존 순서

Excel 작성 -> 수식 연결 -> 결과 확인 -> 설명 자료 작성

제안하는 순서

BM/모델 구조 언어화 -> 필요 시 기존 Excel 분석 -> LLM 대화 -> HTML 구조화 -> 시뮬레이션 -> Excel 구현

Part 26. BM/모델 구조 언어화가 먼저

BM 언어화가 먼저다

기존 Excel 모델 분석은 BM 언어화를 대체하는 것이 아니라 보완하는 자료임.

사람이 직접 파악한 경우

  • BM Brief 작성
  • 사업모델 설명을 드라이버 구조로 변환
  • 가정, 수익원, 비용원, 재무제표 연결 정리

  • 사람이 파악한 BM과 계산 구조 대조

Part 27. BM Brief가 필요한 이유

BM Brief는 통제 장치다

LLM에게 바로 재무모델을 맡기면 그럴듯하지만 평면적인 결과가 나오기 쉬움.

없을 때 생기는 문제

  • 업종 일반론에 가까운 구조 제안
  • 핵심 드라이버 누락 가능성
  • 사람이 통제하기 어려운 가정 생성

답해야 하는 질문

  • 고객, 판매 단위, 과금 단위는 무엇인가?
  • 매출의 Q와 P는 무엇인가?
  • 비용은 어떤 드라이버에 따라 움직이는가?
  • 어떤 가정이 객관적이고 주관적인가?
Part 28. LLM과 Deterministic Model의 역할 분리

LLM과 계산 모델은 다르다

LLM은 확률적 생성 시스템이고, 재무모델은 같은 입력이면 같은 출력이 나와야 하는 결정론적 계산 시스템임.

LLM에 맡기기 좋은 일

  • BM 설명 구조화
  • 매출원과 비용 항목 분해
  • Q x P, 퍼널, 코호트 구조 제안
  • 누락된 드라이버 질문

결정론적으로 닫을 일

  • 숫자 계산과 기간별 수식 전개
  • 회계 항목 연결
  • 이자, 세금, 감가상각, 배당 waterfall
  • 과거 실적 정합성 검증
Part 29. LLM의 역할

LLM은 정답지가 아니다

LLM은 분석가의 생각을 구조화하는 대화 상대이며, 최종 판단은 사람이 해야 함.

LLM이 잘하는 일

  • BM 설명에서 매출원 분리
  • 비용 항목과 매출 드라이버의 연결 질문
  • 객관 가정과 주관 가정 분리
  • HTML 트리에 들어갈 노드 구조 제안

사람이 해야 하는 일

  • 구조 검토
  • 숫자와 단위 확인
  • 과거 실적과 정합성 확인
  • 매출, 비용, 자산, 부채, 현금흐름이 앞뒤 맞게 연결되는지 확인

Part 311. HTML은 무엇인가

HTML은 브라우저에서 열리는 문서 형식임

코딩을 몰라도, 여기서는 HTML을 “웹브라우저가 바로 열 수 있는 문서” 정도로 이해하면 충분함.

문서

  • 제목, 표, 문단, 버튼을 담을 수 있음
  • 하나의 파일로 저장하고 공유 가능함

화면

  • CSS로 색상, 크기, 배치를 조정함
  • 다이어그램과 표를 더 압축해서 보여줌

도구

  • JavaScript로 버튼, 슬라이더, 계산을 넣을 수 있음
  • 읽는 문서가 아니라 조작하는 화면이 됨
Part 311.1 HTML이 마크다운보다 나은 지점

공유하고 조작할 결과물은 HTML이 유리함

마크다운은 쓰기 쉽지만 표현이 제한적임. HTML은 화면 구성, 탐색, 공유, 상호작용을 한 파일 안에 담을 수 있음.

정보 밀도

  • 색상, 표, 그래픽, 이미지 사용 가능
  • 같은 정보를 더 적은 지면에 담음

가독성

  • 탭, 접힘 섹션, 링크를 만들 수 있음
  • 긴 문서도 구조적으로 탐색함

공유

  • 브라우저에서 바로 열림
  • 링크 하나나 파일 하나로 전달 가능함

상호작용

  • 슬라이더, 버튼, 드래그를 넣을 수 있음
  • 값을 바꾸고 결과를 바로 확인함

HTML은 예쁜 보고서가 아니라, Excel에 들어가기 전 모델 구조를 검토하는 인터페이스임.

Part 311.3 LLM이 HTML을 비교적 잘 다루는 이유

LLM은 HTML을 비교적 정확하게 읽고 고친다

HTML은 구조가 태그와 속성으로 드러남. 그래서 LLM이 “이 표”, “이 버튼”, “이 계산 블록”처럼 특정 부분을 집어 수정하기 쉬움.

LLM 입장에서 쉬운 점

  • 문서 구조가 코드 안에 명시됨
  • 화면 요소와 계산 로직을 블록 단위로 나눌 수 있음
  • 수정 전후 차이를 diff로 확인하기 쉬움

재무모델링에서의 의미

  • BM 설명을 드라이버 트리로 바꾸기 쉬움
  • 가정변수와 계산 결과를 같은 화면에 둘 수 있음
  • 코워커가 HTML을 보고 Excel 모델을 직접 구현하기 쉬움

Part 312.1 BM을 드라이버 트리로 볼 수 있음

BM을 드라이버 트리로 본다

말로 긴 설명을 늘어놓기보다, 매출원이 어떤 Q와 P로 구성되는지 먼저 보여줌.

매출 ├─ 구독 매출 = 유료 고객 수 x 월 구독료 x 12개월 ├─ 거래 수수료 = 거래 건수 x 평균 거래액 x 수수료율 ├─ 광고 매출 = 노출 수 x CPM / 1,000 └─ 부가 서비스 = 이용 건수 x 건당 과금액
Part 312.2 매출과 비용의 공유 드라이버가 보임

좋은 모델은 드라이버를 공유한다

매출과 비용이 따로 놀지 않고, 같은 사업 드라이버가 매출, 비용, 자본 부담에 함께 반영되어야 함.

활성 고객 수 ├─ 구독 매출 ├─ 결제 수수료 ├─ 고객지원 인건비 ├─ 서버 비용 └─ 운전자본

핵심 질문

  • 활성 고객 수가 늘면 매출만 늘어나는가?
  • 비용과 자본 부담도 같이 늘어나는가?
  • Excel의 여러 시트에 흩어진 참조가 한 구조로 설명되는가?

Part 312.5 LLM과 협업하기 좋음

HTML은 LLM과 블록 단위로 대화하기 쉽다

여기서 블록은 데이터, 화면 트리, 계산 로직처럼 역할이 분리된 코드 묶음을 뜻함. 특정 블록만 집어서 수정 요청하고 diff로 검토하기 쉬움.

블록역할대화 예시
D모든 변수와 값의 저장소과거 실적과 추정값을 분리해줘
화면 구조화면에 보이는 모델 구조활성 고객 수가 매출, 비용, 운전자본에도 연결되게 해줘
simCalc()시나리오 재계산 엔진금리 변화가 이자비용과 Equity Value에 반영되게 해줘

  • 비용과 매출 드라이버 연결 여부
  • B/S와 이자비용 연결 여부

HTML은 재무모델의 설계도다

Part 414. HTML은 Excel 모델링 지시서

HTML은 코워커가 Excel을 만들 때 보는 설계도임

중요한 것은 중간 파일이 아니라, 코워커가 이 구조를 보고 같은 수식과 시트로 Excel 모델을 구현할 수 있는지임.

구성HTML에서 확인할 것Excel로 옮길 때

Part 415. HTML에서 검토할 질문

HTML에서는 모델 구조를 먼저 맞춘다

화면을 예쁘게 만드는 것보다, 이 구조를 그대로 Excel 수식으로 옮길 수 있는지 확인하는 일이 먼저임.

매출 / 비용

  • 모든 매출원이 빠짐없이 표현되었는가?
  • 각 매출원이 Q x P 또는 퍼널로 설명되는가?
  • 비용이 매출 드라이버와 연결되어 있는가?

재무제표 / 전환

  • B/S, CAPEX, 차입금, 이자비용 연결이 닫혀 있는가?
  • 시뮬레이터에서 핵심 가정을 바꿀 수 있는가?
  • 이 구조를 그대로 Excel로 옮길 수 있는가?

Part 517. 실습 진행 장면

실습은 산출물이 맞물려 바뀌는 장면을 보여준다

수강자는 LLM과 대화하면서 BM md와 HTML을 Excel 모델링 지시서로 다듬는 과정을 봄.

01 · Human
사업모델을 말로 정리

매출원, 비용원, 자금조달 구조를 먼저 문장으로 풀어 씀.

02 · LLM
기존 자료를 구조화

기존 Excel 또는 BM 설명을 분석해 Q, P, 비용 드라이버를 분해함.

03 · Review
누락 드라이버를 잡음

사람이 빠진 매출원, 비용 연결, 공유 드라이버를 지적함.

04 · HTML
HTML 구조 업데이트

트리, 가정변수, 계산 흐름을 고치고 Excel로 옮길 구조를 확정함.

05 · Excel
Excel 모델로 구현

코워커가 합의된 구조를 Excel 시트와 수식으로 직접 구현함.

Excel 구현 중 구조가 바뀌면 BM md와 HTML도 다시 업데이트함

Part 620. 이 방식의 장점

설명 가능성과 검토 가능성이 높아진다

검토자가 셀 참조를 덜 따라가도 모델의 논리와 가정 연결을 이해할 수 있음.

설명

  • 모델 논리를 설명하기 쉬움
  • 투자심사 질문 대응이 빨라짐

검토

  • 공유 드라이버가 드러남
  • 구조적 오류 감소

통제

  • LLM 산출물을 사람이 통제
  • 핵심 가정을 시뮬레이션으로 확인
Part 621. 주의할 점

보기 좋은 HTML이 맞는 모델을 보장하지 않는다

LLM이 만든 숫자와 구조는 모두 검토 대상이며, 최종 계산은 검증 가능한 수식 또는 코드로 닫아야 함.

반드시 확인

  • 단위와 과거 실적 정합성
  • Excel 수식의 참조 방향
  • 재무제표 연결 오류와 중복 계산
  • 누락된 비용과 낙관적 가정

경계 유지

  • LLM이 만든 수식/숫자를 그대로 믿지 않음
  • 최종 계산은 Excel 수식 또는 검증 가능한 코드로 수행
  • 같은 입력이면 같은 출력이 나오는 구조로 모델을 닫음
Part 622. Excel의 역할

Excel은 합의된 모델을 계산으로 닫는 곳이다

BM과 HTML에서 정리한 구조를 실제 수식, 시트, 검토 가능한 파일로 옮기는 마지막 단계임.

계산

  • 기간별 수식 전개
  • P&L, B/S, 현금흐름 연결

검토

  • 셀 참조와 수식 추적
  • 입력값과 결과값 검산

공유

  • 투자심사와 내부 리뷰
  • 제출 가능한 최종 파일
Part 623. 수강자가 가져가야 할 것

수강자가 가져갈 역량

LLM 시대의 모델링 역량은 Excel 속도가 아니라 구조 설계와 검증 능력임.

구조화 역량

  • BM을 재무모델링 언어로 정리
  • 기존 Excel 모델을 LLM으로 구조 분석
  • 드라이버 구조를 만들고 검토

구현 역량

  • HTML 트리로 모델 구조 시각화
  • 핵심 가정을 시뮬레이터로 검토
  • 검토된 구조를 Excel 모델로 구현

좋은 모델은
설명할 수 있어야 한다

Excel을 열기 전에 사업 구조를 말로 정리하고, HTML에서 연결 관계를 확인한 뒤, 마지막에 수식으로 닫는다.

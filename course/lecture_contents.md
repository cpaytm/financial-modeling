## 3. 기존 재무모델링의 출발점

- 전통적 출발점
  - Excel에서 바로 시작
  - 과거 실적 입력
  - 매출과 비용 수식 작성
  - 가정 시트 구성
  - 결과표와 차트 생성

- 장점
  - 실무 표준
  - 계산과 감사에 강함
  - 공유와 제출에 익숙함

- 문제
  - 수식은 많아지지만 모델 논리는 잘 보이지 않음
  - 셀 참조는 연결되어 있지만 사업모델 구조는 숨음
  - 검토자가 숫자의 출처를 따라가느라 큰 그림을 놓침
  - 매출과 비용이 같은 드라이버를 공유하는 지점이 잘 드러나지 않음
  - 투자심사 질문이 들어오면 여러 시트와 수식을 다시 추적해야 함

- 결론
  - Excel은 계산에는 강함
  - Excel은 모델의 논리와 드라이버 관계를 보여주는 데는 약함

## 4. 이 강의가 바꾸려는 순서

- 기존 순서

```text
Excel 작성 → 수식 연결 → 결과 확인 → 설명 자료 작성
```

- 제안하는 순서

```text
BM/모델 구조 언어화 → 필요 시 기존 Excel 분석 → LLM 대화 → HTML 구조화 → 시뮬레이션 → Excel 구현
```

- 핵심
  - Excel을 버리는 것이 아님
  - Excel에 들어가기 전 모델 구조를 먼저 드러냄
  - 드라이버와 가정의 연결을 먼저 검토함
  - 구조에 합의한 뒤 Excel로 계산 모델을 구현함

## 5. 주요 산출물

- BM / Model Structure Brief

  - 사람이 파악한 BM을 정리할 수도 있음
  - 기존 Excel 모델을 분석해 구조를 보완할 수도 있음

- Excel Financial Model
  - 최종 계산 모델

| Excel Financial Model | 계산되는 모델 |

## 6. BM/모델 구조 언어화가 먼저

- 전제
  - 모델링 전에 사업모델과 모델 구조를 언어로 정리해야 함
  - 이 단계는 생략되지 않음
  - 기존 Excel 모델 분석은 BM 언어화를 대체하는 것이 아니라 보완함

- 사람이 직접 파악한 경우
  - BM Brief를 작성
  - 사업모델 설명을 LLM과 함께 드라이버 구조로 변환
  - 가정, 수익원, 비용원, 재무제표 연결을 언어로 정리

- 기존 Excel 모델이 있는 경우
  - 회사 또는 자문사가 만든 Excel 모델을 LLM이 함께 분석
  - 시트 구성, 입력값, 수식, 출력표를 읽어 구조 파악
  - 사람이 파악한 BM과 Excel에 숨어 있는 계산 구조를 대조
  - 복잡한 Workbook을 단순화된 BM/드라이버 구조로 재정리
  - HTML 트리로 옮길 핵심 노드와 가정변수 추출

- 핵심
  - “BM 정리”와 “Excel 분석”은 대체 관계가 아님
  - 사람이 이해한 BM을 기준으로 기존 Excel 분석이 보완 자료가 됨
  - 바로 Excel을 고치거나 새로 만들지 않음
  - 먼저 모델 구조를 언어와 HTML로 드러냄
  - 사람이 LLM의 구조화 결과를 검토함

## 7. BM Brief가 필요한 이유

- LLM에게 바로 “재무모델 만들어줘”라고 하면 생기는 문제
  - 그럴듯하지만 평면적인 결과 생성
  - 업종 일반론에 가까운 구조 제안
  - 핵심 드라이버 누락 가능성
  - 사람이 통제하기 어려운 가정 생성

- BM Brief의 역할
  - LLM에게 주는 재료
  - 사람이 모델링 방향을 통제하는 기준점
  - HTML 트리와 Excel 모델의 원천
  - 기존 Excel 분석 결과를 해석하는 기준

- BM Brief가 답해야 하는 질문
  - 고객은 누구인가?
  - 무엇을 판매하는가?
  - 어떤 단위로 과금하는가?
  - 매출의 Q와 P는 무엇인가?
  - 비용은 어떤 드라이버에 따라 움직이는가?
  - 성장의 병목은 무엇인가?
  - 과거 실적에서 반드시 맞춰야 하는 숫자는 무엇인가?
  - 어떤 가정이 객관적이고 어떤 가정이 주관적인가?

## 8. LLM과 Deterministic Model의 역할 분리

- 전제
  - LLM은 확률적 생성 시스템
  - 재무모델은 결정론적 계산 시스템
  - 두 성격을 구분하지 않으면 모델 신뢰도 하락

- LLM에 맡기기 좋은 일
  - BM 설명 구조화
  - 매출원과 비용 항목 분해
  - Q × P / 퍼널 / 코호트 구조 제안
  - 기존 Excel 시트 구조 요약
  - 누락된 드라이버 질문
  - HTML `D`, `TREE`, `SIM_SECS` 초안 작성
  - 검토자가 확인해야 할 질문 생성

- Deterministic하게 처리해야 하는 일
  - 숫자 계산
  - 회계 항목 연결
  - 기간별 수식 전개
  - 대출 이자 계산
  - 세금, 감가상각, 배당 waterfall
  - 과거 실적 정합성 검증
  - Excel 최종 산출물 생성

- 운영 원칙
  - LLM은 초안과 구조 제안에 사용
  - 계산은 수식, 룰 엔진, Excel, Python으로 닫음
  - LLM이 만든 숫자는 입력값이 아니라 검토 대상
  - 최종 모델은 같은 입력이면 같은 출력이 나와야 함
  - 사람은 LLM의 구조화 결과와 deterministic 계산 결과를 연결하고 검증함

- 강의 메시지
  - LLM을 많이 쓰는 것이 목표가 아님
  - LLM을 써야 할 곳과 쓰면 안 되는 곳을 구분하는 것이 핵심
  - 모델링의 신뢰도는 deterministic하게 닫히는 계산 구조에서 나옴

## 9. LLM의 역할

- LLM은 정답지가 아님
- LLM은 분석가의 생각을 구조화하는 대화 상대

- LLM이 잘하는 일
  - BM 설명에서 매출원 분리
  - 각 매출원을 Q × P 또는 퍼널 구조로 변환
  - 비용 항목과 매출 드라이버의 연결 질문
  - 기존 Excel 파일의 시트 구성과 수식 패턴 분석
  - 복잡한 Excel 모델을 개발/운영/재무제표/배당 구조로 요약
  - 객관 가정과 주관 가정 분리
  - HTML 트리에 들어갈 노드 구조 제안
  - 사람이 놓친 연결 관계 질문

- 사람이 해야 하는 일
  - LLM이 만든 구조 검토
  - 숫자와 단위 확인
  - 과거 실적과 정합성 확인
  - 회계적으로 닫히지 않는 연결 수정
  - 최종 가정 판단

## 10. 좋은 LLM 대화의 흐름

- 한 번에 끝내지 않음
- BM → 구조 → 검토 → 수정 → 구현 순서로 진행

```text
BM / Model Structure Brief
  ↓
필요 시 기존 Excel 구조 분석
  ↓
매출원 / 비용원 / 자금조달 구조 분해
  ↓
Q × P 또는 퍼널 구조화
  ↓
비용 드라이버 연결
  ↓
B/S와 현금흐름 연결 질문
  ↓
객관/주관 가정 분리
  ↓
HTML TREE 설계
  ↓
시뮬레이터 변수 선정
```

- 강의 진행 방식
  - 위 과정을 라이브 실습으로 직접 진행
  - 실제 대화 예시는 강의 후 별도 파일로 축적 가능

### 10.1 대화 중 산출물의 동시 업데이트

- 전제
  - LLM과의 대화는 일회성 프롬프트가 아님
  - 대화가 진행될수록 BM 이해도와 모델 구조가 같이 바뀜
  - 따라서 BM md와 HTML은 동시에 진화함

- BM md의 역할
  - 논리와 언어의 source of truth
  - 사업모델 이해, 드라이버 정의, 가정 근거, 검토 질문을 기록
  - HTML과 Excel이 왜 그렇게 구성되었는지 설명하는 문서

- HTML의 역할
  - BM md를 시각화한 review layer
  - 트리 구조, 연결 관계, 시뮬레이션 변수를 눈으로 검토
  - Excel로 옮기기 전에 구조 오류를 발견하는 작업대

- Excel의 역할
  - 계산과 제출의 final output
  - 합의된 BM/HTML 구조를 deterministic한 수식으로 구현
  - 새로운 논리를 즉흥적으로 발명하는 공간이 아님

- 실제 반복 흐름

```text
LLM 대화
  ↓
BM / 모델 구조 md 수정
  ↓
HTML Framework 수정
  ↓
HTML 검토
  ↓
추가 질문 / 구조 수정
  ↓
BM md와 HTML 재수정
  ↓
구조 확정
  ↓
Excel 구현
```

- Excel 수정이 발생한 경우
  - Excel에서 수식, 시트 구조, 드라이버가 바뀌면 BM md도 수정
  - Excel에서 새로운 계산 구조가 생기면 HTML 트리도 수정
  - Excel만 고치고 BM md와 HTML을 방치하면 세 산출물이 불일치함
  - 불일치가 생기면 수업의 핵심인 설명 가능성과 검토 가능성이 사라짐

- 운영 원칙
  - BM md는 모델 논리의 기록
  - HTML은 모델 구조의 검토 화면
  - Excel은 계산 결과의 실행 파일
  - 세 파일은 위계가 아니라 서로 검증하는 세 층
  - 최종 Excel을 고칠수록 BM md와 HTML도 함께 업데이트해야 함

## Part 3. HTML의 역할

- HTML을 재무모델의 중간 작업대로 정의
- Markdown과 Excel 사이에서 HTML이 맡는 기능 정리
- 재무모델링 관점에서 HTML이 유용한 이유 구체화

## 11. 왜 HTML인가

- HTML은 예쁜 보고서가 아님
- 재무모델링에서의 HTML
  - Excel에 들어가기 전 모델 구조를 검토하는 중간 작업대
  - 드라이버와 가정의 연결을 눈으로 확인하는 인터페이스
  - 시나리오를 조작해보는 간단한 시뮬레이터

- Markdown의 역할
  - BM Brief에 적합
  - 강의 콘텐츠에 적합
  - 원본 메모와 Source of Truth에 적합
  - 복잡한 재무모델 구조 표현에는 평면적

- Excel의 역할
  - 계산에 강함
  - 실무 제출에 강함
  - 감사와 검증에 익숙함
  - 모델 논리와 드라이버 관계를 한눈에 보여주기 어려움

- HTML의 위치
  - Markdown과 Excel 사이의 중간층
  - 생각의 원본과 계산 모델 사이의 구조 검토 인터페이스

```text
Markdown = 생각의 원본
HTML = 구조를 보고 조작하는 인터페이스
Excel = 계산 가능한 최종 모델
```

---

## 12. 재무모델링 관점에서 HTML이 유용한 이유

- HTML이 유용한 이유
  - 단순히 색을 넣고 보기 좋게 만들 수 있어서가 아님
  - 숫자보다 먼저 구조를 드러낼 수 있기 때문
  - 매출, 비용, 가정, 시나리오의 연결을 한 화면에서 검토할 수 있기 때문

### 12.1 BM을 드라이버 트리로 볼 수 있음

- 사업모델을 말로만 설명할 때의 문제
  - 설명이 길어짐
  - 매출원이 섞임
  - Q와 P가 불명확해짐

- Excel로 바로 들어갈 때의 문제
  - 셀과 시트로 흩어짐
  - 사업모델의 구조가 수식 뒤에 숨음

- HTML 트리의 장점
  - BM을 드라이버 구조로 표현
  - 매출원을 계층적으로 분해
  - “이 회사가 어떻게 돈을 버는가”를 먼저 보여줌

```text
매출
├─ 차량대여 = Fleet × 월 렌트료 × 12개월
├─ 거래중개 = Traffic × 상담 신청률 × 전환율 × 건당 수수료
├─ 플랫폼 = 리드 수 × 리드 단가 + 광고 매출
└─ 중고차 = 판매 대수 × 판매가 - 매입 원가
```

### 12.2 매출과 비용의 공유 드라이버가 보임

- 좋은 모델의 조건
  - 매출과 비용이 따로 놀지 않음
  - 같은 사업 드라이버가 매출, 비용, 자본 부담에 함께 반영됨

- 예시: `Fleet`
  - 렌트 매출 생성
  - 보험료 생성
  - 감가상각 생성
  - 차량 취득 자금 필요
  - 이자비용 생성

```text
Fleet
├─ 렌트 매출
├─ 보험료
├─ 감가상각
├─ 차량 취득 자금
└─ 이자비용
```

- HTML의 장점
  - 하나의 드라이버가 여러 노드에 영향을 주는 구조를 시각화
  - Excel의 여러 시트에 흩어진 참조를 한 화면에서 이해
  - 투자심사 질문의 질을 높임

- 핵심 질문
  - Fleet를 늘리면 매출만 늘어나는가?
  - 비용과 자본 부담도 같이 늘어나는가?

### 12.3 가정변수를 모델의 표면으로 끌어올릴 수 있음

- Excel에서의 문제
  - 핵심 가정이 특정 셀에 숨어 있음
  - 어떤 변수가 중요한지 검토자가 바로 알기 어려움

- HTML에서 가능한 표현
  - 가정변수 패널
  - 슬라이더
  - 토글
  - 시나리오 버튼
  - 민감도 표시

- 표면으로 끌어올릴 가정 예시
  - Traffic 성장률
  - 전환율
  - Fleet 신규 투입
  - 평균 렌트료
  - Headcount
  - 급여 단가
  - 차입금리
  - 잔존가치

- 효과
  - 모델이 계산 파일에서 토론 가능한 구조물로 바뀜
  - 투자심사 질문에 바로 대응 가능

### 12.4 시나리오 질문에 즉시 반응 가능

- 투자심사에서 자주 나오는 질문
  - 전환율이 1%p 낮으면 어떻게 되는가?
  - Fleet 도입 속도를 늦추면 현금흐름은 좋아지는가?
  - 금리가 높아지면 영업이익은 얼마나 훼손되는가?
  - 인력 채용을 늦추면 EBITDA는 어떻게 바뀌는가?

- Excel에서도 가능하지만 필요한 과정
  - 시트 이동
  - 데이터 테이블 확인
  - 민감도 표 재계산
  - 수식 참조 확인

- HTML에서의 장점
  - 슬라이더 조작
  - 결과 즉시 확인
  - 가정과 결과의 연결을 같은 화면에서 확인

- 결론
  - HTML은 모델 설명 도구이면서 간단한 시뮬레이터

### 12.5 LLM과 협업하기 좋음

- HTML의 특성
  - 텍스트 코드
  - 구조가 블록 단위로 나뉨
  - LLM이 읽고 수정하기 쉬움

- LLM이 다룰 수 있는 블록
  - `D`
  - `TREE`
  - `INPUT_KEYS`
  - `DEFAULTS_S`
  - `simCalc`
  - `SIM_SECS`

- 예시 요청

```text
Fleet가 감가상각과 이자비용에도 연결되도록 TREE와 simCalc를 수정해줘.
단, 매출 트리의 구조는 유지해줘.
```

- 장점
  - Excel 파일 자체보다 구조화된 코드 블록으로 대화하기 쉬움
  - 사람이 변경 의도를 명확히 지시 가능
  - LLM 수정 결과를 diff로 검토 가능

### 12.6 Excel로 넘어가기 전 구조 오류를 줄임

- 핵심 전제
  - 구조가 틀린 모델은 수식이 맞아도 틀린 모델

- HTML 단계에서 확인할 것
  - 매출원 누락 여부
  - Q와 P 혼재 여부
  - 비용과 매출 드라이버 연결 여부
  - B/S와 이자비용 연결 여부
  - 과거 실적과 맞출 항목
  - 시나리오로 흔들어야 할 변수

- 효과
  - Excel은 새로 생각하는 공간이 아니라 합의된 구조를 계산으로 구현하는 공간이 됨
  - Excel 모델의 구조적 오류 감소

## 14. Framework HTML의 9개 블록

- `framework/template.html`을 채우는 9개 블록

| 번호 | 블록 | 의미 |
|---|---|---|
| 1 | `YRS` | 실적과 추정 연도 |
| 2 | `D` | 모든 변수와 값의 저장소 |
| 3 | `INPUT_KEYS` | 사용자가 조정할 가정변수 |
| 4 | `TREE` | 화면에 보이는 모델 구조 |
| 5 | P&L Table | 결과 테이블 |
| 6 | Assumption Sections | 가정변수 목록 |
| 7 | `DEFAULTS_S` | 시뮬레이션 기본값 |
| 8 | `simCalc()` | 재계산 엔진 |
| 9 | `SIM_SECS` | 시뮬레이터 UI 구성 |

- 진행 방식
  - LLM이 한 번에 완성하지 않음
  - 대화하면서 단계적으로 업데이트
  - 사람이 구조와 가정을 계속 검토

## 20. 이 방식의 장점

- 모델의 논리를 설명하기 쉬움
- 검토자가 셀 참조를 따라가지 않아도 됨
- 매출과 비용의 공유 드라이버가 드러남
- 기존 Excel 모델의 숨은 구조를 빠르게 요약 가능
- LLM의 산출물을 사람이 통제 가능
- 핵심 가정을 시뮬레이션으로 즉시 확인 가능
- 투자심사 중 질문에 더 빠르게 대응 가능
- Excel 모델의 구조적 오류 감소

## 21. 주의할 점

- LLM이 만든 숫자를 그대로 믿지 않음
- LLM이 만든 구조도 그대로 믿지 않음
- HTML이 보기 좋다고 모델이 맞는 것은 아님

- 반드시 확인할 것
  - 단위
  - 과거 실적 정합성
  - Excel 수식의 참조 방향
  - LLM이 생략한 세부 시트나 보조 계산
  - 회계적 연결
  - 중복 계산
  - 누락된 비용
  - 지나치게 낙관적인 가정
  - Excel로 옮길 때의 수식 재현 가능성

- LLM과 deterministic calculation의 경계 유지
  - LLM이 만든 수식/숫자를 그대로 믿지 않음
  - 최종 계산은 Excel 수식 또는 검증 가능한 코드로 수행
  - 같은 입력이면 같은 출력이 나오는 구조로 모델을 닫음
